# 本地模型评测

目的：决定手机上用哪个模型。手机内存和算力有限，只能运行 1～2B 规模的模型；它们能不能把题目“读对、画对”，需要用数据说话，而不是看几个例子。

## 方法

- **题集**：
  - 开发集 `eval/problems.js`，17 道题，覆盖函数、三角函数、平面几何、解析几何、不等式（线性规划）、立体几何、动点问题、应用题；其中 7 道生成了带配图的题目图片（`eval/images/`），用来评测拍照识别。改进作图流程时参考的是这一组题。
  - 保留集 `eval/holdout.js`，19 道题，在改进完成之后、运行任何模型之前写好，题型和措辞与开发集不同（菱形、梯形、弦、角平分线、相似、双曲线、抛物线焦点、长方体、圆锥、正四棱锥、工程问题等），之后不再根据它的结果调整规则。它用来回答“改进是不是只对开发集有效”。
- **流程**：评测脚本直接调用 App 使用的 `public/lib/pipeline.js`，经过本项目的接口（`/api/recognize`、`/api/analyze`、`/api/repair`），评测的就是用户实际得到的结果。分析一律使用题目原文，让“识别”和“作图”两项能力分开衡量。可以比较三种流程：
  - `baseline`：改进前的流程——生成一次，命令出错时修正一次（是否采用由 `public/lib/repair.js` 判定）；
  - `verified`：从题目文字提取条件并核对，题目写明的方程、区域、顶点由程序补画，有错误或条件不满足时把具体问题发给模型修正一次；
  - `best3`：在 `verified` 的基础上，还不满足时最多再重新生成两次（温度 0.7），保留满足条件最多的一版。这是 App 现在的流程。
- **判定“画得对不对”**：每道题都手写了可以自动检验的几何条件，例如 AB = 5、DE ⊥ AC、D 是 BC 中点、函数经过 (3, 0)、立体图的棱长相等且互相垂直。长度允许 2% 误差，角度允许 1.5°。检验函数本身也经过验证：内置示例全部通过，故意画错的图会被检出；保留集的检验条件用手写的参考答案逐题验证过。
- **注意**：App 自己从题目文字里提取的条件和这些手写的检验条件有重叠（都来自题目），所以开发集上的提升会偏乐观；保留集的题目是事后写的，提取规则没有针对它们调整过，更能代表真实效果。
- **运行**：`npm run eval`（需要 Ollama）。结果保存在 `eval/results/`。

## 指标

| 指标 | 含义 |
|---|---|
| JSON 有效 | 模型输出能解析成要求的格式（受 JSON Schema 约束，理论上应接近 100%） |
| 首次作图成功 | 第一次给出的命令全部能执行，且画出了图形 |
| 修正采用 | 首次有错误的题中，自动修正被采用的数量 |
| 最终可执行 | 经过自动修正后，命令全部能执行的比例 |
| 几何条件满足 | 所有题的检验条件中，满足的比例 |
| 完全符合题意 | 所有检验条件都满足的题目比例（最严格的指标） |
| OCR 准确率 | 识别结果与题目原文的字符级相似度（去掉排版差异后计算编辑距离） |
| 题目条件满足 | App 从题目文字里自动提取的条件中，最终图形满足的比例（App 自己的核对，不是评测标准） |
| 程序补全 | 题目写明的方程、区域、顶点模型没画对，由程序补画的题数 |
| 平均调用次数 / 平均耗时 | 每道题调用模型的次数（分析、修正、重新生成都算）和从开始到得到最终图形的总时间 |
| 分析耗时 / 生成速度 / 内存 | 在 M4 Pro（48 GB）上通过 Ollama 测得；手机上会慢一些 |

## 结果二：改进 2B 的作图质量（2026-11-10）

改进分两部分，全部在程序一侧，没有换模型、也没有改提示词：

1. **引擎兼容小模型的写法**：先用后定义、整段重复输出、被 JSON 吃掉反斜杠的 LaTeX、用到却没定义的 O 等（见下方“评测驱动的改进”）。
2. **核对题目条件**（`public/lib/constraints.js`、`pipeline.js`）：
   - 从题目文字里提取长度、角度、垂直、平行、中点、坐标、方程、不等式组等条件，画完后逐条核对；
   - 题目写明的方程、不等式组、平行四边形缺的顶点，由程序直接补画；
   - 有错误或条件不满足时，把具体问题（如“DE ⊥ AC（图中夹角 84.3°）”“缺少点 C”）发给模型修正一次；
   - 还不满足就重新生成（最多再两次，温度 0.7），保留满足条件最多的一版。

### 2B 的效果

保留集（19 道事后写的新题）每种流程跑了 3 轮，共 57 题次；开发集只跑了 1 轮。原始数据：`eval/results/2026-11-10T06-50-24`（开发集 + 保留集第 1 轮）、`2026-11-10T07-22-09`（保留集第 2、3 轮）。

| 2B（qwen3.5:2b-q4_K_M） | 首次生成就完全正确 | **最终完全正确** | 几何条件满足 | 平均调用模型次数 | 平均耗时（M4 Pro） |
|---|---|---|---|---|---|
| 保留集 · 改进前（baseline） | 23% | **23%** | 45% | 1.6 | 6.9 秒 |
| 保留集 · 改进后（best3） | 23% | **40%** | 62% | 3.1 | 14.9 秒 |
| 开发集 · 改进前（baseline） | 47% | **53%** | 81% | 1.4 | 5.3 秒 |
| 开发集 · 只核对和修正（verified） | 35% | **65%** | 81% | 1.5 | 6.0 秒 |
| 开发集 · 改进后（best3） | 47% | **76%** | 93% | 2.2 | 12.7 秒 |

- 两种流程“首次生成就完全正确”的比例相同（保留集都是 23%），说明提升来自流程本身，而不是那几轮模型碰巧发挥得好。
- 保留集上从 23% 提高到 40%，开发集上从 53% 提高到 76%。开发集上的提升偏乐观（提取规则是对照这组题写的），保留集的数字更可信。
- 没有出现“首次生成是对的、经过流程反而变错”的情况。
- 代价是时间：平均调用模型的次数从 1.6 次增加到 3.1 次，耗时大约翻倍。第一版就满足全部条件时不会多花时间。

### 4B 作对照（各 1 轮）

| 4B（qwen3.5:4b-q4_K_M） | 首次生成就完全正确 | 最终完全正确 | 平均耗时 |
|---|---|---|---|
| 开发集 · 改进前 → 改进后 | 71% → 71% | **71% → 88%** | 11.2 → 12.4 秒 |
| 保留集 · 改进前 → 改进后 | 53% → 37% | **53% → 47%** | 10.2 → 20.9 秒 |

4B 保留集的两轮“首次生成”本身就差了 3 道题（53% 与 37%），只跑 1 轮看不出流程的效果；按同一轮比较，改进后的流程把 4B 保留集从 37% 提到 47%。要下结论需要像 2B 一样多跑几轮。

### 还没解决的错误

2B 在保留集上仍然做错的题，大多是模型本身的推理问题，核对能发现，但模型改不对：

- **长度、角度算错**：菱形、梯形、两条切线、长方体，点的坐标与题目数据不符；
- **漏掉题目里的点**：弦题没有 O、C、D，相似题没有 E、C，正四棱锥没有顶点 P，动点题没有 P；
- **立体图的数值不对**：圆锥画成半径 1、高 3；
- **自己算错要求的量**：例如在模拟器上实测时，2B 把 y = x² − 2x − 3 与 x 轴的交点算成 (1, 0)、(−3, 0)（应为 (−1, 0)、(3, 0)），因为“求交点”是问题而不是已知条件，目前的核对不会检查它。

下一步可以做的：让程序按题目要求直接构造要求的点（零点、顶点、交点用 Root、Vertex、Intersect 计算，而不是让模型自己算）；对“点的坐标与已知长度、角度不符”的情况，用一个小的约束求解器在保持模型画法的前提下调整坐标。

## 结论与建议

1. **拍照识别可以完全放在手机上**：0.8B、2B、4B 的 OCR 准确率都是 95%，连最小的 0.8B 都能把题目读对。
2. **作图是瓶颈**：改进前 2B 完全画对 53%，0.8B 只有 24%，与 4B 的 88% 差距明显。小模型主要错在推理（漏定义点、几何关系想错），而且不太会根据报错自我修正（2B 的修正只采用了 1/11）。加入“核对题目条件”后，2B 在保留集上从 23% 提高到 40%（开发集 53% → 76%），代价是耗时约翻倍（见“结果二”）。
3. **手机上的选择**：
   - 默认用 **2B**（约 1.9 GB，视觉投影换成 Q8 后约 1.5 GB），识别和作图都在手机上完成，能接受“一半左右的图需要手动调整”；
   - 8 GB 内存的 iPhone（iPhone 15 Pro 及以后）可以提供 **4B** 作为“高质量模式”（约 3.3 GB 文件），需要真机实测速度与内存；
   - 0.8B 只适合做识别，不适合作图。
4. **提高小模型作图质量的方向**（都可以用 `npm run eval` 量化效果）：
   - ~~由程序从题目里提取条件、画完后自动核对、不符合就修正或重新生成~~（已完成，见“结果二”）；
   - 由程序构造题目要求的点（零点、顶点、交点），不让模型自己算；
   - 用约束求解器修正与已知长度、角度不符的坐标；
   - 为小模型单独写更短、例子更多的提示词。
5. **手机上的耗时**：核对流程平均调用模型 3 次。手机上每次调用都比电脑慢，需要缓存系统提示（见 [ios-plugin.md](ios-plugin.md)），必要时把重新生成的次数从 2 次减到 1 次（`PIPELINE_DEFAULTS.maxAnalyses`）。

## 评测驱动的改进

第一轮评测后逐条查看失败原因，把“模型自然的写法”和“模型真正的错误”分开处理：前者改引擎去兼容，后者交给自动修正或更大的模型。

| 发现 | 例子 | 处理 |
|---|---|---|
| 模型用自己习惯的名字表示坐标轴 | `Intersect(f, x-axis, 1)` | 引擎兼容 `x-axis`、`x_axis`、`x轴`，并在提示词里说明写 `xAxis` |
| 模型想要顶点、零点，但没有对应命令 | `C = Vertex(f)` | 新增 `Vertex`、`Root`、`Extremum`，关键点由程序计算，而不是让模型自己算坐标 |
| 用四个数表示直线 | `Line(-1, 0, 1, 0)` | 引擎兼容 `Line(x1, y1, x2, y2)`、`Segment(x1, y1, x2, y2)` |
| 线性规划写二元目标函数 | `f(x, y) = 2x + y`，再写 `f(B)` | 支持二元函数，可以直接代入点求值 |
| 把函数写成带自变量的形式当参数 | `Intersect(l, f(x), 1)`、`Integral(f(x), 0, pi)` | `f(x)` 出现在需要函数的位置时，就指函数 `f` 本身 |
| 用属性写法取坐标 | `P = (O.x, O.y)` | 兼容 `O.x`，转换成 `x(O)` |
| 小模型陷入重复输出的循环，一道题要 40 秒 | 2B 有两道题写到长度上限 | 输出格式加长度上限（命令最多 60 条等），Ollama 和手机端都会强制执行 |
| 模型自己列方程算交点，算错截距 | 矩形题 `l2: y = 0.25x + 5.5`（应为 6.5） | 属于推理错误；提示词强调用 `Foot`、`Intersect` 让程序计算 |
| 模型漏定义点，后面的命令全部报错 | 圆柱题没定义圆心 O，连带 14 处错误 | 用到却没定义的 O 按原点处理（并给出提示）；其余靠修正 |
| 先用后定义 | `P = (m, f(m))` 写在 `m = …` 前面 | 引擎先跳过，等定义出现后再执行 |
| 整段命令重复输出好几遍 | 相遇问题同一组命令重复 5 遍，24 处“名称已定义” | 完全相同的行只执行一次 |
| LaTeX 的反斜杠被 JSON 吃掉 | `\frac` 变成换页符 + `rac`，`60^\bullet` 变成退格符 | 控制字符后面紧跟字母时还原成反斜杠写法 |
| 标签前多写逗号；坐标式的圆心、圆 | `P = Intersect(f, g, 1), "交点"`、`Center((1, 2))`、`Circle(0, 1, 2)` | 引擎兼容 |
| 用两个数表示括号的两端 | `Brace(0, 360, "360 千米")` | 当作 x 轴上的一段 |
| 引擎自身的问题 | `R = Region(…)` 被当成二元函数，区域画不出来 | 已修复（评测中补画区域时发现） |
| 图能画出来，但不符合题意 | 平行四边形漏了顶点 C；椭圆没画；可行域没画；正方形边长不对 | 核对题目条件 + 程序补画 + 针对性修正 + 重新生成（见“改进 2B 的作图质量”） |

几何检验也帮助发现了引擎自身的问题：`sin 2x` 曾被解析成 `sin(2)·x`，后来通过“程序理解的公式”显示出来并修复。

## 局限性

- **题量小**：开发集 17 道、保留集 19 道，只能看出明显差距。审查报告建议扩充到 50～100 道，往 `eval/problems.js` 或 `eval/holdout.js` 里加题即可，每道题写上几何检验条件。
- **有随机性**：分析时温度为 0.2，同一模型两次运行的结果会有几道题不同（实测 4B 在保留集上两轮的“首次生成就正确”分别是 53% 和 37%）。比较两种流程时，要么多跑几轮（`--runs 3`），要么按同一轮里“首次生成”和“最终结果”成对比较。
- **检验条件不是全部题意**：检验的是关键数量关系（长度、角度、垂直、中点、函数取值），没有检验图形是否美观、标注是否齐全。
- **速度和内存是在电脑上测的**：M4 Pro 上的生成速度会明显高于 iPhone；手机上的实际速度、内存、发热要在真机上另外测。
- **OCR 图片是程序生成的**：清晰、正对、无光照问题，比真实拍照容易；真实照片需要另外收集测试。
