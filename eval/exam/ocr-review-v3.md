# 过去问集：手机引擎的识别结果逐题核对（原模型 / 第三版识别 LoRA，2026-11-12）

- 识别：手机 App 用的同一份引擎（Mac 版 llm-cli，`native/local-model/tools/`），Qwen3.5 2B Q4_K_M + 视觉部分 mmproj。和 App 一样清理结果，文字太少时换个说法重新识别一次（`train/ocr/eval_ocr.mjs`）。
  - 原模型：结果在 `ocr/phone-base/`（重新识别 6 题）
  - 第三版：加上识别 LoRA（`train/adapters/ocr-v1` → `adapter-ocr.gguf`），结果在 `ocr/shuxing-ocr-v1/`（重新识别 0 题）
- 核对方法：Claude 把两份结果逐题和题目图片对照，73 题全部核对（不是抽查）。你的原话：「不要抽查 全部都检查一遍」。
- 另外用 App 预览同一套渲染（KaTeX）把三份结果（含 Ollama 版）的公式全部渲染一遍，看有没有显示出错的（`node train/ocr/latex_check.mjs <结果名> … --list`）。
- 结论分三类，和 `ocr-review.md` 相同：
  - ✓ 正确：和原文一致（只差空格、标点、全角半角、LaTeX 写法）
  - △ 小错：不影响题意（漏了题号、个别字写成中文、个别助词）
  - ✗ 影响题意：式子、条件错了或漏了，题干缺失，或者编造了内容
  - 本轮补充一条：公式写坏（括号、`$` 不配对），App 里显示成红色报错、看不出原式的，也算 ✗。Ollama 版的 73 份结果用同样的渲染检查没有一处显示出错，所以这条补充不影响 `ocr-review.md` 的结论。
- 说明里只写错在哪里，不抄原文。

## 发现的问题（只记录；按过去问集的规则，不根据它调整识别的提示词和训练数据）

1. **第三版在生成的评测图上几乎全对，在真实过去问上明显变差。** 生成的评测图 150 张：字符准确率 99.8%（原模型 60.5%）；过去问 73 题：影响题意的从 4 题变成 34 题。生成的评测图和训练数据出自同一套模板，主要衡量的是“像不像训练数据的写法”。原因推测（没有单独验证）：真实试卷的句子更长、一句里条件更多、排版也不同，LoRA 学到的是模板的写法，遇到长句容易漏掉半句，或者把式子改成见过的样子。
2. **第三版的公式写得更“讲究”（`\dfrac`、`\displaystyle`、`\left…\right`），也更容易漏掉收尾的括号**：14 题显示出错，原模型 0 题。
3. **第三版把九大 10 题答题说明里的“記入しなさい”（请填写）全写成了“記入しない”（不填写）。** 不影响题目，但说明它会把没见过的句子改成训练里常见的样子。
4. **好的一面**：第三版没有整题或半段译成中文的（原模型整题 2 题、部分 2 题；第三版只有 3 题各有一个字词写成中文），没有编造图形描述（原模型 1 题），也没有触发“文字太少”的重新识别。第三版 73 题都没写【图形】，原题里有图的 meidai-2025-4 两份都漏了图。
5. **结论：第三版识别 LoRA 不放进手机 App。** 手机安装包的模型文件夹里只有 `model.gguf` 和 `mmproj.gguf`，引擎只有在文件夹里有 `adapter-ocr.gguf` 时才启用识别 LoRA，所以 App 现在仍用原模型识别，不需要改代码。
6. 要改进识别，需要更像真实试卷的训练数据（长句、多条件、真实排版和扫描效果），并在另一组真实题目上挑选训练步数，而不是在生成的评测图上挑。这一组过去问已经用来发现了上面这些问题，下一版识别的效果要在新的一组题（其他大学或年份）上衡量才公平。
